# tradecli 批量订单研究

日期：2026-10-01。基线：0.2.0-dev.1。范围：Codex、macOS、Parallels、Windows 同花顺。
本次为能力调研、代码审查和只读性能实验，没有新增交易委托，也没有关闭交易确认设置。

## 结论

优先实现 tradecli 批量任务：整张订单表预检、单次启动 Windows 执行端、逐笔校验与状态记录、统一核对结果。
模拟账户可以作为执行验证环境。实盘仅准备和核对订单，最终交易提交由用户操作。
当前客户端的拆单功能与多股票订单篮子应使用不同的能力名称。

## 性能实验

此前十笔模拟买入测试：从第一笔填单到最终委托截图为 330.222 秒，CLI 累计 211.356 秒。
结果为九笔已受理、一笔未确认；已核对订单在观察时均未成交。未确认订单未自动重发。

其中确认调用累计 37.399 秒，读取并关闭成功提示累计 23.387 秒，共 60.786 秒。
这些数字包含进程启动和虚拟机通信，不能全部归因于界面确认。

本次只读资金查询对照：

| 方式 | 十次读取的主机端耗时 |
|---|---:|
| 十次独立 CLI 调用 | 27.704 秒 |
| 一次 Windows 进程，复用客户端连接 | 2.663 秒 |

复用进程内部：连接约 0.643 秒，十次资金读取合计 1.071 秒。
这是一轮只读样本，未进行分布统计。独立 CLI 还包含部署检查和操作记录，工作量并非完全相同。
结论是减少跨虚拟机启动和重复连接具有收益，不能声称订单吞吐提升十倍。
下单速度必须用完整批量执行实测，分别报告纯执行、人工/Agent 复核及异常处理耗时。

## 建议接口（尚未实现）

- `batches validate --input orders.json`：离线校验数据结构和重复项。
- `batches prepare --input orders.json --account <id>`：读取当前账户和资金，形成不可变批次及总额预览。
- `batches run-simulated --batch <id> --digest <hash>`：一次启动执行已授权的模拟订单表。
- `batches status --batch <id>`：查看逐笔进度、合同编号、错误和是否需要介入。
- `batches reconcile --batch <id>`：对照当前委托，输出已受理、拒绝、未执行、结果未知；成交状态独立报告。

订单文件只含有序行号、方向、六位代码、限价、股数。账户通过明确参数绑定。
价格与股数使用字符串；预检包括有限正数、重复项、总买入金额、费用余量和卖出可用数量。
行情来源与获取时间单独记录。各市场交易单位与价格限制应有明确支持范围，不能假设所有证券规则相同。
批次摘要绑定账户、订单内容、顺序、总额上限和有效期。变更任何字段均形成新批次。

## 执行机制

1. 获取桌面互斥锁，连接客户端一次，核对账户和模拟身份。
2. 每笔填单前验证当前页面类型、账户、字段单位；使用已验证的完整选中输入和读回校验。
3. 保存提交尝试状态后触发提交；匹配确认框内的账户、方向、代码、价格和数量。
4. 在发送确认动作前保存确认尝试状态；轮询有限时间等待结果，禁止因等待超时再次下单。
5. 识别成功合同后保存回执；仅关闭该订单已识别的成功提示，清理本批次拥有的草稿，再继续。
6. 碰到未知弹窗、验证码、身份变更、拒单或无回执时停止整批；保留已完成订单与未执行队列。
7. 执行结束统一核对委托。接受委托、成交和撤单分别记录。

批次状态：prepared → running → completed / needs_attention。
订单状态：queued → prepared → submit_attempted → confirm_attempted → accepted / rejected / unknown。
`accepted` 不是 `filled`。中断恢复先查询已有结果，不直接重跑批次或重复未知订单。

需要先重构单笔动作复用层，再增加批次编排。现有 dispatch 会检查 pending 操作，
直接递归调用时可能把正在运行的批次当作阻塞者；不能通过跳过全部 pending 检查解决。
执行所有权必须绑定 batch ID 和互斥锁，其他请求继续被阻止。

主机当前超时为 120 秒；批量任务需要可查询的后台作业或可持续读取进度的传输，
主机超时必须显示“执行状态未知/需要查询”，不能显示“没有提交”或自动重试。
第一版可采用一次性批次进程，无需先建设长期后台服务。

## 可靠性优先事项

- 先定位确认后无回执问题：记录确认前后窗口句柄、标题、按钮、时间和对话框变化。
- 当前代码按单笔固定等待；改为有上限的状态等待，确认失败必须可定位。
- 控件编号在单笔、拆单、双向页面会复用，页面验证不能只依赖买入按钮文字。
- 运行时不得关闭用户的未知弹窗或擦除用户已有草稿。
- 订单受理回执应先落盘，再关闭提示；关闭提示失败不能抹去已受理的事实。
- 改变窗口位置通常不影响控件定位；页面、焦点和可交互桌面仍是执行前提。

## 验证顺序

1. 离线测试：文件结构、金额、摘要、账户绑定、过期、部分成功与未知结果、崩溃后的防重。
2. 只填单验证：多股票连续填单、移动窗口、页面误切与焦点干扰，全部不提交。
3. 经授权的少量模拟订单：比较批次预览、确认框和最终合同。
4. 十笔模拟测速：完整报告成功、拒绝、未知、未执行数量及两种耗时。
5. 实盘保持用户最终提交；智能交易终端的订单篮子作为单独适配路线研究。

本次研究已完成源码和页面证据核对、官方产品能力核对及只读进程复用实验。
批量执行接口尚未实现；没有使用本次结果宣称批量交易已验收。
